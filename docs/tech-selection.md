## 3. バックエンド(言語・フレームワーク)

### 3.1 要件から見た、バックエンドの役割

- 1 人専用のパスワード認証、ログイン状態の管理、ログアウト時のサーバー側での無効化(tech-stack.md 4 章)
- タスクの追加・編集・削除・移動・並び替えの API。並び順の振り直し、競合の検知(updated_at)を含む(db-definition.md、screen-requirements.md 5.7)
- サーバー側での入力値の検証(文字数、必須、category の値)、ログインユーザーごとのデータ分離、CSRF 対策、セキュリティヘッダー(requirements.md 5 章)
- 自動テストの対象となる処理(並び順の振り直し、入力値の検証、ログインの判定、他ユーザーのデータへのアクセス制御)

### 3.3 観点が衝突している点(判断が必要)

- Spring Boot は、「要件の適合性」と「保守のしやすさ」が強みだが、「無料または低コストでの運用」と「開発の難易度」で、課題がある(追加コスト: メモリの確保、Docker 化、休止からの起動待ちの許容)
- Node.js は、「無料での運用」と「手軽さ」が強みだが、認証・セキュリティを自分で組む手間がある
- 「初級編の学習範囲との相性」は、教材の中心となる言語が分からないと、判断できない(確認事項)

### 3.8 費用の方針(確定)

- 【確定】今回は学習目的で、まずアプリが動作するところまで確認できれば十分。月額費用は、0 円を希望する。有料サービスの契約は行わず、無料枠の範囲内で構成を検討する
- 【確定】Spring Boot を学習する方針は維持する(採用技術としての確定は、構成の承認後)

### 3.9 無料構成(第一候補。最終判断は、後続の技術選定を進めたうえで行う)

**提案する組み合わせ**

| 層 | 候補 | 無料での運用 |
| --- | --- | --- |
| バックエンド | Spring Boot(Java)。Docker のコンテナとして動かす | Render の無料ウェブサービス |
| フロントエンド | React / TypeScript。画面のファイルを、Spring Boot が一緒に配信する(1 つのサービスにまとめる) | 同じ Render のサービス |
| データベース | PostgreSQL | Neon の無料枠 |

**この構成を提案する理由**

- 学習範囲(Spring Boot、React / TypeScript、DB / SQL)に合う
- 3 階層を、費用 0 円で動かせる見込みがある
- フロントエンドとバックエンドを、同じサービス(同じ URL)から配信すると、別のサイトを経由しない。iPhone の Safari は、別のサイトの Cookie を既定でブロックするため、ログインの判定が失敗する問題を避けやすい(実装時に確認が要る)。あわせて、CORS の設定が不要になり、CSRF 対策も単純になる
- DB を、別のサービス(Neon)に分けると、Render の無料 DB の期限(30 日)の問題を避けられる

**無料で実現するための制約・妥協点**

1. 休止と起動待ち: 15 分アクセスがないと休止し、次のアクセスで、約 1 分+Spring Boot の起動時間(数十秒)がかかる。初回表示に、1〜2 分かかることがある(要件で許容済み。読み込み中の表示を確定済み)
2. メモリ 512MB: JVM のメモリ設定の調整が必要。起動に失敗する、または不安定になるリスクがある。実際に動かして確認する必要がある。うまくいかなければ、別の構成(下記)を検討する
3. 再起動: Render は、いつでも再起動することがある。サーバーのメモリにログイン情報を持つ方式だと、再起動で、ログインが切れる。ログイン状態を DB に保存する方式などが要る(認証方式の選定で扱う)
4. バックアップ: Neon の無料枠の履歴は 6 時間。大事なデータは、手動(pg_dump など)で書き出す運用になる(確定済みの方針: 自動がなければ手動)
5. データベースの休止: 5 分使わないと休止し、再開に数百ミリ秒かかる(影響は小さい)
6. 無料枠の変更: 無料枠は、条件が変わることがある。決める時点と、運用の途中で、確認が要る
7. 学習範囲の AWS / Terraform は、この構成では使わない。学習のために、AWS の無料プラン(6 か月)を、別に試すことは可能

**うまくいかないときの代替案(未承認)**

- JVM を調整しても、512MB で動かなければ、Google Cloud Run の無料枠(無料枠の数字と、クレジットカードの登録の要否は、未確認)を検討する
- AWS の無料プラン(6 か月)に、Spring Boot を載せる。期間限定になる
- Node.js をバックエンドにする(学習範囲の外になる)

### 3.10 決定

- 【確定】3.9 の無料構成(Render の無料ウェブサービス + 同一サービスでのフロントエンド配信 + Neon の PostgreSQL)を、無料構成の第一候補とした。ただし、DB の選定を保留したため(1.1 章)、Neon の PostgreSQL の部分は、DB の決定まで保留する。Render + 同一サービスでの配信の考え方は、記録として残す
- 【確定】現時点では採用技術として確定しない。後続の技術選定(データベース、フロントエンド、API の形式、認証方式、ホスティング構成など)を進めたうえで、最後のまとめ(2 章の 9)で、最終判断する
- 【確定】512MB のメモリ制限は、リスクとして残す。実装開始後の最初の小さな単位で、Spring Boot の起動・動作を検証する。動作が不安定な場合は、代替案(3.9 章)を比較する
- 【未決定】バックエンドの採用技術(最終判断待ち)

## 4. データベース

### 4.1 要件から見た、データベースの役割

- users と tasks の 2 テーブル。1 対多([db-definition.md](db-definition.md))
- 並び順(position)の一意制約: (user_id, category, position)。並び替え時の一時的な番号重複への対処は、API 設計で検討する引き継ぎ事項
- 競合検知のための更新日時(updated_at)、タスクの物理削除
- 無料での運用(Render は再起動でファイルが消えるため、サーバー内のファイルに保存する DB は使えない)

### 4.2 候補の比較(たたき台)

| 候補 | メリット | デメリット | 今回のアプリとの相性 |
| --- | --- | --- | --- |
| PostgreSQL(Neon の無料枠) | Spring Boot(JPA)で標準的。無料の管理サービス(Neon、1GB、休止あり、復元履歴 6 時間)がある。並び替えで番号が一時的に重なる問題を、トランザクションの終わりまで検査を遅らせる設定(遅延可能な一意制約)で、対処しやすい | 休止(5 分)から、再開に数百ミリ秒かかる。復元履歴が短い | 確定済みの要件(一意制約、トランザクション)に合い、無料構成の第一候補と一致する |
| MySQL | 教材で使うなら、学習と一体にできる。広く使われている | 無料の管理サービスの選択肢は、未調査。遅延可能な一意制約がなく、並び替えの番号の振り直しに、工夫が要る | 教材の DB 次第。無料での運用は、要調査 |
| SQLite(ファイル) | 設定が不要で、軽い | Render の無料枠は、再起動でファイルが消える。複数端末からの利用にも向かない | 今回の構成には、合わない |
| H2(Java の組み込み DB) | Spring Boot の学習やテストに便利 | メモリ上だと、再起動でデータが消える | 本番には使えない。自動テストでの利用は、候補 |

- 【確定】2026-11-17 の方針: データベースの選定を保留する。PostgreSQL は、仮候補・第一候補ではなく、比較候補として保留する(1.1 章)

## 5. フロントエンド

### 5.1 要件から見た、フロントエンドの役割

- PC のドラッグ&ドロップ(分類間の移動、同じ分類内の並び替え)、スマホの長押しメニュー、編集モードでの長押しドラッグ(screen-requirements.md 7 章・UC-06・UC-07)
- 操作の直後に画面へ反映し、保存失敗なら元に戻す(画面と状態の管理が重要。screen-requirements.md 5.2)
- ダイアログ、通知メッセージ、読み込み中・エラーの表示、ダークモード、レスポンシブ(横並びと縦積みの切り替え)
- Mac・iPhone の Safari での動作(タッチ操作を含む)

### 5.2 候補の比較(たたき台)

| 候補 | メリット | デメリット | 今回のアプリとの相性 |
| --- | --- | --- | --- |
| React + TypeScript(ビルドは Vite など) | 教材の範囲と一致する。画面の状態管理、ダイアログ、楽観的な更新(先に反映して、失敗なら戻す)を、扱いやすい。ドラッグ&ドロップのライブラリが豊富 | ビルドの設定が要る。画面のファイルを、Spring Boot に載せる手順(同一サービスでの配信)の整備が要る | 学習範囲に合い、要件の複雑な画面操作にも向く |
| Vue など、ほかのフレームワーク | 書きやすいと言われる | 教材の範囲外で、追加の学習が要る | 学習範囲との相性で、不利 |
| サーバーで画面を作る方式(Spring Boot の Thymeleaf など)+ 素の JavaScript | ビルドが不要で、Spring Boot だけで完結する | ドラッグ&ドロップ、先に反映して失敗なら戻す動き、通知、ダイアログを、JavaScript で手書きする量が多い。画面の状態管理が複雑になりやすい | この画面操作の量には、向かない |
