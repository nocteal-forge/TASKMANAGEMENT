## 3. 公開方針・端末間の同期・競合

- 【確定】初級編では、無料のホスティングサービスなどを利用して、インターネット上に公開する方針を維持する。ただし、フロントエンド・バックエンド・データベースの 3 階層を運用できるサービス構成は、技術選定の段階で検討する
- 【確定】PC・スマートフォンの両方から URL でアクセスできるようにする
- 【確定】PC・スマートフォン間のデータ同期は、同一のデータベースを参照することで実現する
- 【確定】同期を実現するうえで、認証・アクセス制御を含めた設計が必要(4 章)
- 【確定】初期リリースでは、独自ドメインを取得せず、ホスティングサービスが提供する URL を使用する。将来、必要性が出てきた場合は、独自ドメインへの変更を検討できるようにする
- 【未決定】具体的なホスティングサービス(技術選定の段階で決める)
- 【確定】初期リリースでは、他の端末での変更を自動では反映しない。画面を再読み込みしたときに、最新のデータを取得する
- 【確定】古い表示のまま操作した場合に、データや並び順が意図せず上書きされないようにする
- 【確定】他の端末とのデータの食い違いを検知した場合の方針
  - 食い違いが検知された操作は、保存しない
  - サーバーから最新のデータを取得し、画面を最新の状態に戻す
  - 画面下部に、赤系の通知を表示する
  - ユーザーは、最新の状態を確認してから、もう一度操作する
  - 競合の検知には、tasks の既存の項目 updated_at を利用する(データ設計の項目は変わらない)
- 【確定】競合を検知したときの通知
  - 文言は、「他の端末で変更されています。最新の状態を読み込みました。もう一度操作してください。」とする
  - 保存失敗時のエラー通知と同じ部品を使い、赤系で表示する。自動では消さず、ユーザーが閉じるまで表示する
  - 編集ダイアログで保存・削除が食い違った場合は、ダイアログを閉じ、最新の状態を読み込み、同じ通知を表示する。入力途中の内容は破棄する
  - 他の端末で削除済みのタスクを操作した場合は、保存せず、最新の状態を読み込み、同じ通知を表示する
  - 画面上の詳細は [screen-design.md](screen-design.md) 5.7

## 4. 認証・アクセス制御


### 確定事項

- 【確定】1 人専用のパスワード認証を採用する。ユーザー登録機能は設けず、自分専用のアカウント・パスワードでログインする
- 【確定】認証は、ログイン画面だけでなく、バックエンド API へのアクセスにも適用する(未ログインでは API でデータを読み書きできない)
- 【確定】基本的なセキュリティとして、次の観点を考慮する
  - パスワードの安全な保存(平文ではなく、パスワードハッシュで保存する)
  - ログイン状態の管理
  - HTTPS 通信
  - 総当たり攻撃(パスワードを繰り返し試す攻撃)への対策
- 【確定】ログアウト操作を設ける。ログアウト時は、ログイン画面に戻すだけでなく、サーバー側でも認証状態(ログイン状態)を無効化する。ボタンは、メイン画面のヘッダー右側に置く([screen-design.md](screen-design.md) 4.1)
- 【確定】認証切れ(ログイン状態の期限切れ)の扱い([screen-design.md](screen-design.md) 2.1)
  - サーバーへ操作を送信したタイミングで検出する。画面を開いたまま放置している間は、定期的な認証確認を行わない
  - 検出したら、ログイン画面へ移動し、メッセージを表示する。再ログイン後は、メイン画面へ戻る
  - 認証切れで失敗した操作は、保存せず、自動で再実行もしない。入力途中の未保存の内容は、失われてよい
- 【確定】パスワードを忘れたときは、開発者(自分)がサーバー側の設定またはデータベースから再設定する。メールによる再設定機能は実装しない。ログイン画面には案内やリンクを設けない
- 【確定】初期アカウントは、サーバー側で作成する(運用手順として行う。[database-design.md](database-design.md))
- 【確定】初級編では 1 人専用とする。将来のマルチユーザー対応を妨げない設計が望ましい(ただし対応自体は今回の対象外)

### 未決定事項(技術選定・認証方式の選定で決める)

- 【未決定】具体的な認証方式(例: セッション方式、トークン方式など)。メリット・デメリットを説明したうえで相談する
- 【未決定】パスワードの保存方法の詳細(ハッシュの方式)、ログイン状態の保持期間
- 【未決定】総当たり攻撃への具体的な対策(例: 失敗回数の制限など)
- 【未決定】パスワードの初期設定・変更の方法(運用手順として整理する)

2. Mac・iPhone の Safari への対応

- 【確定】特定の技術を最初から採用前提にしない。Java の Spring Boot も含めて、公平に比較する
- 【確定】一度にすべてを決めず、1 項目ずつ確認しながら進める

### 7.9 無料構成(第一候補。最終判断は、後続の技術選定を進めたうえで行う)

**提案する組み合わせ**

| 層 | 候補 | 無料での運用 |
| --- | --- | --- |
| バックエンド | Spring Boot(Java)。Docker のコンテナとして動かす | Render の無料ウェブサービス |
| フロントエンド | React / JavaScript(Vite でビルド)。画面のファイルを、Spring Boot が一緒に配信する(1 つのサービスにまとめる) | 同じ Render のサービス |
| データベース | PostgreSQL | Neon の無料枠 |

※ 2026-11-19: この表の Docker は、**本番環境で Spring Boot をコンテナ化する【提案】**(Render で動かすため)。講義10で使われた、開発環境で PostgreSQL を動かす Docker / Docker Compose(5.3 章)とは、**別の用途**である。

**この構成を提案する理由**

- 学習範囲(Spring Boot、React / JavaScript、DB / SQL)に合う
- 3 階層を、費用 0 円で動かせる見込みがある
- フロントエンドとバックエンドを、同じサービス(同じ URL)から配信すると、別のサイトを経由しない。iPhone の Safari は、別のサイトの Cookie を既定でブロックするため、ログインの判定が失敗する問題を避けやすい(実装時に確認が要る)。あわせて、CORS の設定が不要になり、CSRF 対策も単純になる
- DB を、別のサービス(Neon)に分けると、Render の無料 DB の期限(30 日)の問題を避けられる

**無料で実現するための制約・妥協点**

1. 休止と起動待ち: 15 分アクセスがないと休止し、次のアクセスで、約 1 分+Spring Boot の起動時間(数十秒)がかかる。初回表示に、1〜2 分かかることがある(要件で許容済み。読み込み中の表示を確定済み)
2. メモリ 512MB: JVM のメモリ設定の調整が必要。起動に失敗する、または不安定になるリスクがある。実際に動かして確認する必要がある。うまくいかなければ、別の構成(下記)を検討する
3. 再起動: Render は、いつでも再起動することがある。サーバーのメモリにログイン情報を持つ方式だと、再起動で、ログインが切れる。ログイン状態を DB に保存する方式などが要る(認証方式の選定で扱う)
4. バックアップ: Neon の無料枠の履歴は 6 時間。大事なデータは、手動(pg_dump など)で書き出す運用になる(確定済みの方針: 自動がなければ手動)
5. データベースの休止: 5 分使わないと休止し、再開に数百ミリ秒かかる(影響は小さい)
6. 無料枠の変更: 無料枠は、条件が変わることがある。決める時点と、運用の途中で、確認が要る
7. 学習範囲の AWS / Terraform は、この構成では使わない。学習のために、AWS の無料プラン(6 か月)を、別に試すことは可能

**うまくいかないときの代替案(未承認)**

- JVM を調整しても、512MB で動かなければ、Google Cloud Run の無料枠(無料枠の数字と、クレジットカードの登録の要否は、未確認)を検討する
- AWS の無料プラン(6 か月)に、Spring Boot を載せる。期間限定になる
- Node.js をバックエンドにする(学習範囲の外になる)

### 10.3 API 設計(試行案)

- 【提案】(試行実装方針・承認済み)以下の構成を、試行案とする。講義 11 の `GET /api/tasks` などは参考であり、正式仕様としては採用しない。講義の status を使う API(`/api/tasks/status/{status}`)は採用しない

| 操作 | HTTP メソッド | エンドポイント | 補足 |
| --- | --- | --- | --- |
| タスク登録 | POST | /api/tasks | 成功は 201 |
| 一覧取得 | GET | /api/tasks | |
| 詳細取得 | GET | /api/tasks/{id} | |

- 【提案】(試行実装方針・承認済み)内容更新では、メモ・期限日のクリアに null を使う。必須項目の欠落と、明示的な null は区別する(欠落は、不正なリクエストとして扱う)
- 【提案】(試行実装方針・承認済み)HTTP ステータスコード: 200 処理成功 / 201 新規作成成功 / 204 処理成功・応答本文なし / 400 入力・リクエスト不正 / 404 対象が存在しない / 409 競合
- 【提案】(試行実装方針・承認済み)エラー応答は、エラーコード方式を基本とする(例: TITLE_REQUIRED、TITLE_TOO_LONG、MEMO_TOO_LONG、CATEGORY_INVALID、CONFLICT、NOT_FOUND)。画面に表示する日本語のメッセージは、既存の確定仕様(screen-design.md、database-design.md 6 章)に従い、画面側が、コードから対応づけて表示する
- 【提案】(試行実装方針・承認済み)新規登録は、4 分類すべて(「完了」を含む)で受け付け、その分類の列の末尾に追加する(position は、その分類の最大値 + 1。空なら 1)。分類間の移動の配置ルールとは別の操作として扱う(screen-design.md 7 章)

- 【提案】(試行実装方針・承認済み)認証の実装前に、ローカル環境でタスクの登録・取得を検証するため、暫定ユーザーを使う。正式な認証機能とは別のもので、認証の実装時に撤去する
- 【提案】(試行実装方針・承認済み)「現在の利用者」を返す部品 `CurrentUserProvider` を使い、Service は、この部品だけに頼る
- 【提案】(試行実装方針・承認済み)暫定ユーザーは、`dev` プロファイル(環境ごとに、設定や部品を切り替える Spring の仕組み)でのみ使える。`dev` は、明示的に指定した場合だけ有効にする
- 【提案】(試行実装方針・承認済み)暫定ユーザーの `login_id` は、開発用であることが分かる名称にする。正式なログインには使えない設計とし、ローカル開発環境からのみアクセスできるようにする
- 【提案】(試行実装方針・承認済み)`dev` 以外の環境で、暫定ユーザーが使えないことを、テストで確認する
- 【提案】(試行実装方針・承認済み)作成方法は、起動時に存在を確認し、無ければ作成する方式を、採用候補とする。**DB への書き込みと、暫定ユーザーの作成は、Phase 1 の開始時に、別途承認を得る**。テスト用データの管理と、テスト用 DB の分離も、その時点で提案する
- 4 章の認証(未ログインでは API でデータを読み書きできない)は、確定仕様である。暫定ユーザーは、認証の実装前の、ローカル開発での検証のための、試行上の例外であり、4 章の確定仕様を変更しない

### 10.6 入力検証(試行案)

- 【提案】(試行実装方針・承認済み)専用の検証部品 `TaskInputValidator` を作り、検証処理を 1 か所に集約する。登録と更新で、共通の規則を使う。文字数は、Unicode のコードポイントで数え、`String.length()` の値は使わない。不正な入力は保存しない。サーバー側でも、必ず検証する。検証処理の単体テストを用意する。新しい依存関係は、追加しない
- 【提案】(試行実装方針・承認済み)フロントエンドとバックエンドで、同じ入力検証の規則を使う
- 【提案】(試行実装方針・承認済み)規則は、次のとおり(database-design.md 6 章の確定仕様を、具体化した試行案。確定仕様は変更しない)

| 項目 | 規則 |
| --- | --- |
| タイトル | 必須。100 コードポイントまで。前後の半角スペース・全角スペース・NBSP(ノーブレークスペース)を除去する。タイトル内の改行は不可。空白だけの場合は、登録・更新できない |
| メモ | 任意。1,000 コードポイントまで。前後の半角スペース・全角スペース・NBSP を除去する。メモ内の改行は許可する。空白だけの場合は、NULL として保存する |
| 期限日 | 任意。時刻を含まない日付 |
| 絵文字 | Unicode のコードポイントで数える |

- 【未決定】除去対象とする空白文字の一覧(タブやその他の Unicode 空白文字の扱い)、CR・LF・CRLF などの改行の扱いと、メモの改行コードを統一する必要性、日付の形式と、存在しない日付の検証方法。Phase 1 の実装前に、具体的な定義を提示する

### 10.7 競合検知の方針(試行案)

- 確定仕様: 競合の検知には、既存の項目 updated_at を使い、食い違いが検知された操作は保存しない(3 章、screen-design.md 5.7)
- 【提案】(試行実装方針・承認済み)**条件付き UPDATE** で、競合の確認と更新を、不可分(原子的)に行う。id、user_id、更新前の updated_at が、すべて一致する場合だけ、更新する。古い updatedAt による更新は拒否し、409 を返す。更新に失敗したときは、データを部分的にも変更しない。成功したときは、更新後の最新データを返す
- 【提案】(試行実装方針・承認済み)JPA の `@Version` には、置き換えない
- 【提案】(試行実装方針・承認済み)フロントエンドは、updatedAt を、競合検知用の文字列として保持し、JavaScript の Date に変換しない(変換すると、時刻の精度が欠落するため)
- 【提案】(試行実装方針・承認済み)同じ updatedAt を使った 2 つの更新要求で、片方だけが成功することを、検証する
- 【提案】(試行実装方針・承認済み)分類移動・並び替えに伴う、複数行の競合検知は、Phase 3 で、別に設計する
- 【未決定】updated_at の時刻の生成方法。PostgreSQL の `now()` は、トランザクションの開始時刻を返すことを考慮し、更新後の値が、更新前の値より、確実に新しくなる方法を、DB の時刻精度、同一時刻での更新、時計の逆行も含めて検討する。Phase 2 の開始前に提案する

### 10.8 Git・GitHub 運用(要約)

- 【提案】(試行実装方針・承認済み)機能単位の作業ブランチと PR(Pull Request)を使う。`main` は安定版とし、直接のコミット・push は、原則として行わない。ブランチ名は、`docs/`(文書)、`feature/`(機能実装)で始める。push は、`-u` を使わず、リモート名とブランチ名を明示する。PR の作成・マージは、ユーザーの承認後に行う。詳細は、CLAUDE.md を参照
